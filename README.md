# 보안 프로토콜 기반 1:1 안전 메시지 시스템

사용자 간 1:1 메시지에 **공개키 암호화**와 **전자서명**을 적용하여
메시지의 **기밀성·무결성·인증·부인방지**를 보장하는 메시지 시스템.

서버는 **평문 메시지를 절대 볼 수 없고**, **개인키를 절대 보관하지 않는다.**
모든 암호화·복호화·서명은 사용자 브라우저에서 이루어지는 종단간(E2E) 구조다.

---

## 빠른 시작

```bash
# 1. 의존성 설치
npm install

# 2. 서버 실행
npm start

# 3. 브라우저에서 접속
#    http://localhost:3000
```

테스트 실행:

```bash
npm test
```

> 참고: 이 앱은 DB를 자동 선택한다. 환경변수 `DATABASE_URL` 이 있으면
> **PostgreSQL**(배포·외부 DB용)을, 없으면 `better-sqlite3` 설치 시 SQLite를,
> 그것도 없으면 JSON 파일 저장소를 쓴다. 로컬에서는 설정 없이 바로 실행된다.
> 어느 쪽이든 기능은 동일하다.

## 사용 방법

1. **회원가입** — 사용자명/비밀번호 입력. 이 시점에 브라우저가 RSA 키쌍
   2개(암호화용·서명용)를 생성한다. 공개키만 서버로 전송되고, 개인키는
   이 브라우저의 IndexedDB에만 저장된다.
2. **메시지 보내기** — 받는 사람을 고르고 내용을 입력하면, 수신자의 공개키로
   암호화하고 내 개인키로 서명한 뒤 전송한다.
3. **받은 메시지** — 내 개인키로 복호화하고, 송신자 공개키로 서명을 검증한다.
   검증 결과가 각 메시지에 배지로 표시된다(✔ 검증됨 / ✖ 실패).

## 보안 설계

### 키 구성 (사용자당 RSA 키쌍 2개)

| 용도 | 알고리즘 | 역할 |
|------|----------|------|
| 암호화 | RSA-OAEP (2048bit, SHA-256) | 메시지 기밀성 |
| 서명 | RSA-PSS (2048bit, SHA-256) | 무결성 + 송신자 인증 |

암호화용과 서명용 키를 분리한 것은 암호학적 모범 사례다(키 용도 분리 원칙).

### 하이브리드 암호화

RSA는 키 길이보다 긴 데이터를 직접 암호화할 수 없다. 그래서 다음 방식을 쓴다.

1. 메시지마다 1회용 **AES-256-GCM** 대칭키를 생성
2. 그 키로 본문을 암호화 (`ciphertext`, `iv`)
3. AES 키 자체를 **수신자의 RSA-OAEP 공개키**로 암호화 (`encKey`)

수신자는 자신의 RSA 개인키로 AES 키를 풀고, 그 AES 키로 본문을 복호화한다.

### 전자서명

송신자는 **평문 원문**에 대해 RSA-PSS 서명을 만든다(`signature`).
수신자는 복호화로 평문을 복원한 뒤, 송신자 공개키로 서명을 검증한다.

### 메시지 처리 흐름

```
[송신자]  작성 → 서명(개인키) → AES암호화 → AES키를 RSA암호화 → 전송
[서버]    암호문·암호화된키·IV·서명만 저장 (평문 접근 불가)
[수신자]  AES키 RSA복호화 → 본문 AES복호화 → 서명 검증(송신자 공개키) → 출력
```

### 보장되는 보안 속성

- **기밀성** — 수신자의 개인키 없이는 누구도(서버 포함) 복호화 불가
- **무결성** — 암호문 변조 시 AES-GCM 인증 태그 불일치로 복호화 단계에서 실패
- **인증** — 서명 검증으로 송신자 신원 확인
- **부인방지** — 송신자 개인키로 만든 서명이 증거로 남음

## 관리자 기능

**첫 번째로 회원가입한 사용자가 자동으로 관리자가 된다.** 별도 설정은 필요 없다.

관리자로 로그인하면 화면 하단에 관리 패널이 나타나며 다음을 할 수 있다.

- 전체 사용자 목록과 각 사용자의 메시지 송수신 건수 조회
- 사용자 삭제 (해당 사용자가 주고받은 메시지도 함께 삭제됨)

단, **관리자도 메시지 내용은 볼 수 없다.** 메시지는 수신자의 개인키로만
복호화되고 그 개인키는 서버에 없으므로, 관리자가 볼 수 있는 것은 암호문과
통계뿐이다. 이것은 이 시스템의 종단간 암호화 설계에 따른 의도된 동작이다.

안전장치로 관리자는 자기 자신을 삭제할 수 없다(관리자 부재 방지).

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET    | `/api/admin/check` | 현재 사용자가 관리자인지 확인 |
| GET    | `/api/admin/users` | 전체 사용자 + 메시지 통계 (관리자만) |
| DELETE | `/api/admin/users/:id` | 사용자 삭제 (관리자만) |

> 관리자 권한은 JWT에 담기지만, 삭제 같은 민감한 작업은 매번 DB에서
> 권한을 다시 확인한다(권한 박탈 후 남은 옛 토큰을 막기 위함).

## 기술 스택

- **백엔드**: Node.js + Express (REST API)
- **인증**: JWT(세션 토큰) + bcrypt(비밀번호 해싱)
- **저장소**: PostgreSQL(외부 DB·배포) / SQLite / JSON 파일 — 환경에 따라 자동 선택
- **프론트엔드**: 순수 HTML/CSS/JavaScript (ES 모듈)
- **암호화**: 브라우저 Web Crypto API (RSA-OAEP, RSA-PSS, AES-GCM)
- **개인키 보관**: 브라우저 IndexedDB

## 한계 및 주의사항 (학습용 프로젝트)

- 개인키가 브라우저 IndexedDB에만 있으므로, 브라우저 데이터를 지우거나
  다른 기기에서 접속하면 이전 메시지를 복호화할 수 없다(설계상 트레이드오프).
- 공개키 신뢰는 서버를 통한 TOFU(Trust On First Use) 수준이며,
  중간자(MITM) 방지를 위한 키 지문 검증·인증서 체계는 포함하지 않았다.
- JWT 시크릿은 `JWT_SECRET` 환경변수로 주입하는 것을 권장한다
  (미설정 시 개발용 기본값 사용).
- 실서비스에는 HTTPS, 비밀번호 정책 강화, 키 백업/복구 전략이 추가로 필요하다.
